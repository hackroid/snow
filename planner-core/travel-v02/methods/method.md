# 方法（不变量）— 住宿/套餐检索固定流程 v0.2

变量（spec、报价、库存、错误、来源、比较）按 batch 存放在 `data/batches/`；本文件只放不变量。
改条件（日期/人数/泊数/雪场）后旧报价一律失效，不混用、不沿用。

## 1. 规格（每批先行，缺项标 unknown 不假设）
出发日（＝第一天滑雪日）、泊数、雪场、人数与分房（几名几室）、餐食要求、停车需求、预算（可无）。
普通周末通常 1 泊；2 泊看节假日/用户年假，不查私有日历、不替用户决定请假。
默认：全员成人；每个滑雪日都需雪票（ticket_days_needed 默认＝滑雪天数），有人持季票/雪マジ资格时在 spec 按人另注、那部分不计票；**装备不进 spec 筛选**（无“无需租具”这类过滤项），只作为结果权益逐产品记录。

## 2. 套餐检索（Orion 起点，Skiichiba 同套路）
1. 用 `tools/orion_link.py` 按 spec 生成链接（参数映射见 `orion-params.md`，以页面回显验证为准）。URL 能拼 ≠ 搜索成功。工具不可用时按 `orion-params.md` 映射表手工构造（2026-11-11 复用测试验证可行）。
   **通道前提**：列表与日历只经真实浏览器呈现，文本抓取读不到（2026-11-11 两次实证）。无真实浏览器时停在回显验证层，只报通道限制——不跳过列表拼候选、不用其他日期的价格凑本 spec 总价。
2. 页内确认：回显的出发地/日期/泊数/雪场正确；排序切到「安い順」（SortType 参数不可依赖）；人数在详情阶段以室人数设定（sj 参数不回显）。
3. 两个住宿预设都查：入口默认「宿おまかせ」＋页内改「宿泊条件を選択」（不限定）。翻完分页，记录来源总数与实际覆盖（读了几件、未读/阻断几件），不虚称搜全。
4. 按ツアーコード跨预设、跨平台去重（Orion 与 Skiichiba/tramaru 是同一运营后台，同产品双店面不算两个独立报价；价格以各自实读为准并注明）。
5. 优先核最低价 10 个或全部可得候选的详情：餐食按原文逐日核（首日晚＋次日早常见但不是保证）；含票天数与票种；**第二天起的票看产品级选项**（无票→2日券选项、含1日券→升2日券，边际价以产品页当轮实读为准；留意有无单卖第二天券的产品形态）；资格限制单列（雪マジ/プリンス20 等年龄・身份权益、女性限定等，资格未知不当普通可订）；停车与到雪场步行/送迎；**位置必须分开记**：住宿所属雪场/入口（本地雪场）与步行距离指的是哪个雪场，写明“本地（XX雪场）：徒歩X分”；目标雪场与本地雪场不同时，另记到目标雪场的方式（自驾/接驳）与季节性设施状态（如 Dragondola 开通日，以雪场官网为准），未核写 unknown，不许把本地雪场的步行距离写成到目标雪场的距离；取券点与最早时间；取消条件（无原文则 unknown）；**票种范围单列**（雪场专用券 vs 共通券，权益范围不同不得写成相同）；**装备权益**：含/不含/可加购/unknown、范围（整套/单项）与天数、额外金额、费用性质（可退押金/维护费/保险）与退还条件——押金金额逐产品核，未核到就 unknown。费用必须按品类单位记（如免責補償料：板套装/衣服各一份价），不把多品类合成“每人每天一个价”。

## 3. 散订（OTA＋票）
- 酒店：Agoda 优先（本批实测唯一能直接给指定日整单价的渠道），再补一个可用渠道交叉核设施/餐食。OTA 通常不含票，以具体权益为准。
- 票：先以目标雪场官网当季一般公开价为基准（价格为当轮变量，不预置于方法）。优惠渠道按 opportunities 方法逐项核（适用日期/权益/资格/手续费/取票/退款），不把待核优惠当已可用；渠道细节存当轮批次证据，方法只留核法。
- 散订总价 = 房价（整单）＋票（按人×天数口径换算）＋已知附加（停车/入汤税等）；缺项列出，不完整不称总价。
- 优惠渠道的逐项细节（取票/退款原文）按 batch 存放在 `data/batches/` 的证据文件里，本节只留摘要与指针——这是刻意的分工，不是缺失。

## 4. 同口径总价与排序（tools/totals.py 实现）
- 每人总价 = 基础每人价 ＋ 所需票的加购（已含的天数不重复计）；整组 = 每人 × 人数（散订房价按整单进入再均分，注明口径）。
- unknown 价格不当 0、不当最便宜：缺价或加购未核的进“不完整区”，不参与比价排序。
- 软参考（经验，不是过滤器）：1 泊 2 日含所需票 ≤30,000/人；2 泊 3 日 ≤40,000/人。超参考照列并标旗标，不隐藏。
- 排序：可比完整价从低到高；超软参考者留在原位加旗标；不完整区单列在后。
- 可退押金单列为临时支付，**不计入**每人/整组消费总价（在表格备注中单列金额与退还条件，unknown 就写 unknown）；维护费/保险等实际消费若金额已核则计入并注明，未核金额只作备注。
- 套餐内的票或租具不用时**不擅自减价**：只有产品原文允许减额/退款时才按原文调整。

### 4.1 报价口径：积分不入主价（本项目口径示例，权威条款）

- 适用于一切带积分的渠道（Yahoo!トラベル、楽天トラベル、一休等，含未来新增渠道）：**检索、计价、排序、汇报一律用"不抵扣任何积分的房价＋已核必付费用"作主价**。积分即便是常驻或等级权益、"99% 常有"，也不进主价、总价、排序或主比较参考式。
- 积分回馈、ポイント即時割引（即时抵扣）、用既有积分余额支付，都只作**备注**：备注须区分其性质——常驻/等级/活动限时/其他条件/未知——并附已知条件；备注中的积分后金额不得写成报价、不得进参考小计式。
- 本节所说原价/基准价指**排除积分影响的房价**：正常的非积分折扣价（如平台限时降价、不可退款折扣）照常用作主价，不强制改回划线原价；被排除的只是积分这一层。
- 本条是本项目口径示例、不是平台事实：渠道学习或平台展示方式变化不自动改变此口径；改口径须由项目所有者明确指示。

## 5. 跨平台归组（tools/totals.py 的 group 规则）
1. 同一性用“名称＋住所”再加至少一项硬特征（电话/官网/部屋数级/特征设施）判定；番地尾数级出入不单独否定，但须交叉确认。
2. 同名但硬特征对不上 → 标“同名未确认”，不合并。
3. 归组只归“宿”，不归“报价”：房型、餐食、含票、取消、决済、价格各自独立保留；比较只在同房型＋同餐食＋同取消内做，条件不同并列注明差异。
4. 宿おまかせ永不猜具体酒店，独立成条，不借用具名酒店信息。
5. 设施级事实可跨平台互补但标来源；冲突时并记、以公式系/多数源暂定、标待现地确认。
6. 平台专属字段（取消政策、积分、会员价）不外推到同宿其他平台报价。

## 6. 行程依赖与输出
- 每个候选保留：取券地点/最早时间、餐食预约要求、停车与步行/送迎、Dragondola 等季节性交通前提（以雪场官网为准）。
- 输出表字段：每人/整组已知小计（仅住宿＋所需票，表头与口径注必须写清“已知小计、非完整出游消费”，未核的维护费/停车/另付餐费另列不计入；散订每人价为整组均分四舍五入、以整组为准）、基础价＋票加购拆分、住宿/おまかせ、餐食、装备权益（状态/范围/天数/额外金额/费用性质/退还条件）、本地雪场步行/送迎与到目标雪场方式（分开两项）、票种范围、限制资格/取消、原始搜索链接与产品直链（跨平台同产品保留各平台自己的链接）、查询时刻、推荐理由、实际覆盖、还需用户回答的问题。

## 7. 新鲜度与复用
- 同一 spec 的结果在同一雪季、同一预订窗口内可复用为“上次观测”，必须标查询时刻；库存与价格随时变动，**预订前必须按原链接再核**，不承诺有效期。
- 用户可要求刷新；刷新产生新 batch，不覆盖旧 batch。
- 新学习先记为候选（history），有重复证据后再更新本方法，并保留回退说明；单次零结果不改规则。

## 8. 路线观测（酒店 → 目标雪场，驾车）
- **目的地点先行统一**：先用雪场官网的 access/停车信息核对山麓入口/停车场名称，全批所有路线共用同一个目的地点；不得导航到山顶、不得用别的雪场或酒店自有雪场代替。本项目妙高杉之原的目的地点＝第2駐車場（ゴンドラのりば下段，官网 26-27 停车公告 princehotels.co.jp/ski/myoko/informations/26-27parking/）；地图无此 POI 时退回雪场本体（山麓/ゴンドラ一带）并注明实际采用的终点标签。确认的是"点"，不由此臆断停车费等其他事实。
- **模式与来源固定**：Google Maps 驾车路线（ルート検索・車），时间设置用默认"现在出发"，并逐条记录观察时刻。起点按已有证据的名称+地址核对防重名；报告地图实际使用的起终点标签与路线来源链接。
- **km/时长是动态变量**：地图给的距离与时长是观察时刻的估算，按（起点， 目的地， 观察时刻）记录，不是常量——不得固化进方法或当作其他日期/时刻的保证；12 月雪天等实际路况待临近复核。地图见收费道路/冬季封闭等提示则记，未见记未见。
- **缺失处理**：地图没给路线就记 unknown 并留页面原话/原因；不用直线距离、步行、电车、车站送迎或别的雪场车程替代。每条路线最多重试一次，遇访问限制停该线。
- **与报价分离**：路线观测以 route_observations 按物件组随批提交，与房价分开存；新读路线**不刷新**报价的读取时刻与价格有效性判断。路线远近不作住宿过滤器——距离未知不淘汰住宿。
- **源间营业状态冲突随物件展示**：地图或其他来源对物件营业状态的标记（如 Google Maps「閉業」）与报价来源不一致时，不裁定真伪、不据此改报价或断言实际关店；在该物件标题/路线附近直接提示（标记来源＋营业状态待核＋旧报价仅作留档、采用前复核），不能只藏在全页缺项里。
