# method（conditions-v01）— 判断步骤、新鲜度与失效分支

## 1. 每批观测的固定字段（缺一标 unknown，不猜）

每条观测必须同时给出五种时间中的相关项，互不替代：
1. **计划时间**：计划开业/关闭日期（官网予定）——只是计划。
2. **状态时间**：状态页自身的更新时刻（页面标注的更新日時）；页面没标就写 unknown，不得用读取时间代替。
3. **预报发布时间**：JMA reportDatetime。
4. **适用时段**：预报/警报针对的日期与时段（timeDefines），与发布时间分开写。
5. **读取时间**：本方抓取的 JST 时刻。

影像另加：**影像时间**（画面/页面自带的拍摄或更新戳）；没有就写 unknown。直播流（YouTube 等）与静止画分开记：直播流以"读取时流在线/离线"记状态，不写拍摄时间；静止画以其更新戳为准。注：直播的**流标题**可含旧日期（八方 2026-11-11 实查样本：标题写 2026-03-09 而画面内时钟为当前时刻）——标题日期不是影像时间，判读以画面内时钟为准。

## 2. 判断步骤（按序）

1. 先开雪场官网**本季（26–27）**状态/ゲレンデ情报页：记计划开业日期、当前营业状态原词（如 Closed／シーズン外／運行中）、缆车逐条状态、积雪口径（山顶/山麓、cm）。页面标题/内容属于旧季（25–26 以前）→ 整页排除并在批次里注明"旧季已排除"，不得摘录其数值。
   **新鲜度门（2026-11-11 用户纠正后新增）**：状态模块自带戳距读取时间已明显超过其更新节奏时（如季前静态戳已过数日），**当前实际状态一律标"待核/过时"**，模块里的数值只作"旧快照"另列并带数据时间，不得写成当前实况。计划开业日期必须带年份与雪季（如 2026–27 季、2026-11-28），它属于计划/推断层：可以写"按计划尚未到开业日"，但**不得用计划覆盖实况**（计划未到 ≠ 已核实未开放，计划已过 ≠ 已核实开放）。
2. 再开官网 livecam 原入口：记机位、静止画/直播流、影像时间或 unknown。影像戳距读取时间超过该页的通常更新间隔且无新戳 → 标"影像可能过时"，只报入口存在，不报画面内容。
   **入口存在性分类（2026-11-11 用户收紧）**：只有三档——"确认存在"（实见页面本身）、"已查范围未发现/仍待核"（本次所查导航/页面内没定位到入口，只说明本范围未见，留下批复核）、"站点不提供"（**仅当官网明示不提供**时可用；聚合站说法、一次未见、季前未上线都不构成此档）。记录时保留实际核查页 URL、核查时间、确认范围与未知项。
3. JMA 预报：用 methods/sources.md 的官方 JSON。记 reportDatetime、适用日期、天气/降水概率/气温（地点 series 有才写）。一周预报只到其 timeDefines 末日；**目标日期在末日之后 → 该项写"超预报范围，无法预测，待临近复核"**，禁止外推、禁止用气候平均或往年同日代替。**原始快照与日期关联（2026-11-11 验收固定）**：取数时把原始 JSON 响应整文件随批保存（raw 快照），后续核对只认快照、不认转述；数值按原始数组以真实日期关联——先核 timeDefines 与 weatherCodes/pops/reliabilities 等长，再按日期字符串逐日对应（不凭下标记忆）；数组中的空字符串保持空，不补 0、不外推。证据叙述与原始数组矛盾时以原始数组为准；没有原始快照的旧批，其数值只能标待核——事后新取数与旧派生数值一致，也**不追溯证明**旧批那次未保存的取数，旧批证据不足与矛盾记录保留为历史。
4. JMA 警报：用官方 warning JSON 并核对副本的 reportDatetime 是否为近期（同一发布周期内）；副本明显过时（如跨季）→ 记"未取得（接口过时副本）"，**不得写成"无警报"**；需当前状态时改用浏览器开官方警報・注意報页面复核。
5. AMeDAS 积雪：先查 latest_time.txt 定数据时刻，再读对应 map JSON 的目标点 snow 值。雪场官方积雪（山顶/山麓）与 AMeDAS 平地观测点是两个口径，并列记，不互相替代。
   **新鲜度三方比对（2026-11-11 补）**：latest_time 本身也可能是过时缓存，两份时间自洽不等于当前。必须同时比：（a）latest_time 与**本批真实读取时刻**之差、（b）观测时刻与 latest_time 之差；沿用 1 小时阈值，任一超阈值 → 标"过时/待核"；时间戳落在未来、或时区/格式异常 → 同样标待核，不采信。短例：① latest_time 与观测同为 3 小时前（两者都旧）→ 过时，即使两者一致；② latest_time 是 10 分钟前、观测却停在 2 小时前（latest 新、观测旧）→ 该点过时/待核；③ latest_time 5 分钟前、观测在其 10 分钟内（两者新）→ 当前可用。历史批次保留原读取时刻与原证据，不回头重采覆盖；用户要当下实况时才开新批读取。
6. 出行条件卡（与 travel-v02 组合）：按 travel 的日期＋雪场逐项对齐——计划开业（官网予定）、实际开放（仅当季内且状态页为当日更新时可写）、天气预报（在 JMA 窗口内才有值）、警报、影像。任一项超窗/未开放/未取得就按原词显示，不留空、不填估计值。

## 3. 新鲜度与刷新建议（本项目不自动执行，只作建议）

| 类型 | 数据自带节奏 | 建议复核点 | 过时判定 |
|---|---|---|---|
| 官网营业/缆车状态 | 营业日当日多次更新；季前为静态予定 | 出发前一日晚＋当日出发前 | 状态页更新戳不是当日（季内）→ 只作参考，标"需复核"；戳已过数日（季前静态）→ 实况标"待核/过时"，数值按旧快照带数据时间另列（新鲜度门，§2.1） |
| 官网积雪/雪质 | 通常每日朝更新 | 当日朝 | 戳为昨日以前 → 标过时 |
| JMA 短期预报 | 每日 05/11/17 时发布 | 每次发布后 | reportDatetime 超过 6 小时且已跨发布点 → 用新版 |
| JMA 一周预报 | 每日 11/17 时 | 行程进入 7 日内起每日 | 目标日在覆盖末日后 → 超窗，不显示数值 |
| JMA 警报 | 随发布即时 | 出发前与当日 | 副本 reportDatetime 非近期 → 未取得，不下结论 |
| AMeDAS | 每 10 分钟 | 临近出发 | 三方比对（§2.5）：latest_time 距本批真实读取时刻、或观测时刻距 latest_time，任一超 1 小时 → 过时/待核；时间戳为未来或时区异常 → 待核。两者自洽但都旧，同样过时 |
| Livecam 静止画 | 数分钟至 1 小时级 | 当日 | 更新戳落后读取时刻明显超过其惯常间隔 → 只报入口 |
| Livecam 直播流 | 实时流 | 当日 | 流离线/季外停播 → 记离线，不报画面 |

## 4. 失效分支（出现即按此处理，不绕行）

- 官网状态页打不开或只有旧季页 → 该场状态记"未取得"，可退到官网本季お知らせ的开业公告记计划日期，实际状态仍 unknown。
- JMA JSON 结构变更/404 → 换同体系官方入口（forecast 页 HTML）读一次；仍失败记原始错误与入口，不用第三方天气站替代。
- 警报接口返回过时副本（B 线 2026-11-11 实况：副本停在 2026-05-26）→ 记未取得；浏览器复核官方警报页后才可写当前状态。
- Livecam 无时间戳 → 影像时间 unknown，只报"入口存在＋读取时可见/不可见"，不描述画面雪况。
- 目标日期超出一切官方预报窗口 → 条件卡整行显示"待临近复核"（复核点＝进入 JMA 一周预报覆盖后，即出发前 7 日内），不提前生成预测内容。
- 强风/大雪等导致停运：只转述官网/JMA 原词与时刻，加"需临近复核"提示；不替用户判断是否成行、不做安全保证。
